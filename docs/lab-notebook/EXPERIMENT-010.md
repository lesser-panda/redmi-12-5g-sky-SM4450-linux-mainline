# E032 — synthetic load / soak test (unattended, 2026-11-13)

User request: run a continuous synthetic load test while they sleep, to see whether the system is stable and whether anything else needs fixing before the project is called a success.

## Setup (plan, written before the run)
- **Device:** Redmi 12 5G running Debian trixie + GNOME from recovery_b, **m22** (kernel Image a5a0ea4d…, `uname -v` #108, recovery_b image b9dd59b9…). Cable on the laptop (USB gadget network 192.168.7.1 + WiFi <phone-wifi-ip>), no dock. Battery 96–97 %, charger input managed by the kernel limit (75/80). Android/slot untouched; nothing is written to partitions other than ordinary files on the Debian root (sda22, 54 GB free).
- **Tools installed on the phone for the test:** stress-ng, fio, glmark2-es2-wayland, iperf3 (apt, trixie). Not added to tools/debian-roots.txt (test-only).
- **Scripts:** tools/loadtest.sh (phone, systemd transient unit `sky-loadtest`), tools/memhog.py, tools/loadtest-host.sh (laptop watcher). Results on the phone in /root/loadtest/<timestamp>/ and copied to private/e032/ afterwards.
- **Cycle (≈ 29 min, repeated):** A 7 min stress-ng 8×cpu (matrixprod) + 2×vm; A2 3 min memory hog (6.9 GB of 7.3 GB, half incompressible) + 4 cpu → zram/swap; B 1 GiB direct randwrite with crc32c verify + 3.5 min random read (≈ 12 GiB written over 12 cycles); C 5 min glmark2 off-screen on the real GPU (Mesa freedreno, FD612) + 2 cpu; D 5 min WiFi download (3 MB/s cap) + gateway ping + socket stress; E 4 min idle. Every cycle ends with a health check (failed units, gnome-shell, gdm, evdi, OOM kills, battery state and thresholds). A sampler logs every 15 s: load, battery capacity/status/current/temperature, cpu0/cpu6 frequency, MemAvailable, swap, zram, new filtered kernel messages.
- **Laptop watcher** (every 20 s over USB and WiFi, ~100 MB USB transfer every ~80 s): counts failures on both paths; exits with code 2 if both fail 6× in a row (phone down).
- **Safety / limits:** load runs at nice 10; load pauses while battery temperature > 43 °C or capacity < 40 %; no suspend at any time (nothing could wake it); `kernel.panic=15` set at runtime so a kernel panic reboots (into Android) instead of leaving the phone dark; sshd/GNOME/NetworkManager/logind/journald get oom_score_adj −900 (runtime only); duration 6.5 h. **Not tested:** the dock (cable is on the laptop), audio (the user is asleep), Bluetooth, camera/sensors (not enabled).
- **Known blind spot:** the DT has no SoC thermal zones (only the battery sensor, `thermal_zone0`), so Linux cannot see or throttle on SoC temperature; the guard uses battery temperature. CPU max frequencies in this DT are low (policy0 979 MHz, policy6 1104 MHz), which limits heat.

## Pass criteria
No hang/reboot; ssh reachable throughout (watcher failures ≈ 0, short WiFi hiccups documented); no kernel BUG/Oops/WARNING/soft lockup/RCU stall/hung task/GPU fault/UFS error/WLAN firmware crash in `kernel-new.log`; no OOM kill of system services (the hog may be killed); fio verify errors = 0; gnome-shell and gdm alive at every health check; zram/swap used and released; battery temperature stays < 43 °C; charge limit keeps the battery in 75–80 % band or above the floor (input suspended/resumed correctly); evdi module still loaded.

## Fallback
If the phone hangs: hold power ~10 s (boots Android), volume-up + power boots Debian from recovery_b (m22); Debian's persistent journal (var/log/journal on sda22) holds the evidence. If the test misbehaves but the phone is up: `systemctl stop sky-loadtest`.

## Aftermath: audio fell back to Dummy Output (2026-11-13 morning)
- Cause (journal of boots −2…0, all hands-free autoroot boots): `/init` mounts sda22 and switches root ~2 ms after start; the ADSP/APM sound-card probe runs in that same window and asked `qcom/sm8450/Redmi-12-5G-tplg.bin`, which only existed in the initramfs → `-ENOENT`, `snd-sc8280xp probe failed -2`, "No soundcards found". Kernels #106/#107 (m20/m21) probed one step later ("Parent card not yet available", deferred) and won the race; m22 (#108) lost it on both boots. Not caused by the load test (card was absent from boot).
- Live fix (reversible, phone rootfs only): copied the topology to /lib/firmware/qcom/sm8450/ and re-bound `snd-sc8280xp` → card `Redmi125G` back, PipeWire shows the Speaker sink and Bottom microphone again, amp watcher running.
- Durable fix: m23 now builds the topology into the kernel (CONFIG_EXTRA_FIRMWARE, dir private/audio/tplg) so it no longer depends on which root is mounted. m23 NOT built yet (`! tools/build-m23.sh`, which also carries PM_DEBUG). Verify after boot: no "Direct firmware load … tplg" line and `cat /proc/asound/cards` shows the card on a cold boot, 3 boots in a row (race is timing-dependent).
- Lesson: any firmware a late-probing driver requests must be in the kernel image or on the real root, not only in the initramfs. Other initramfs-only files: adsp/wpss images (loaded by remoteproc before switch_root, fine), BT/touch/GPU firmware (also on the rootfs, verified GPU; BT/touch work in current boot).
- Still userspace: FS1599 amp watcher (sky-amp-watch + sky-fs1599, TECH_DEBT) — moving the amp into a kernel codec/DAPM driver is the proper follow-up; it was not the cause of this failure.

### E033 follow-up: bottom speaker silent after the m23 boot (2026-11-13 ~09:20)
- Symptom (user): earpiece works, bottom speaker silent. Kernel/DT/mixer path was fine (RX macro DSM regs 0x5b4/0x5c0/0x5cc = 0/2/1 as in the m18 recipe; UCM routes correct; amp I2C probe OK).
- Finding: FS1599 registers showed the amp ON when idle but OFF (reg 0x03=0, 0x10=1, 0x11=0) as soon as a stream played. Two `sky-amp-watch` processes were running: the desktop user's and a **root** one in root's systemd user manager (started by my root ssh logins; the unit is enabled globally). The root copy watches root's PipeWire (none) → "node gone" → amp off, fighting the user's copy.
- Fix: `ConditionUser=!root` in audio/sky-amp-watch.service (deployed live to /etc/systemd/user/, root instance stopped). With only the user's watcher the amp stays on during playback (reg 0x03=0x0d, 0x11=0xc0). Rootfs builds get it through audio/install-target.sh. Ear confirmation by the user pending.
- Lesson: anything enabled with `systemctl --global` also runs for root's user manager whenever root has a login session; a user-session unit must exclude root, and audio tests over ssh as root can themselves break the speaker. My earlier "1 kHz loopback" numbers in this session (−113/−121/−129 dBFS, even for the earpiece) were taken through the same fight and with a mic path that recorded silence; treat them as invalid.

## E034 plan: FS1599 speaker amplifier in the kernel (m24, prepared 2026-11-13, not yet built or booted)
- **Why:** userspace `sky-amp-watch` follows the PipeWire node, so the amp comes on ~0.1 s after the sound starts (clipped starts), needs an i2c-dev udev rule and a root-visible /dev/i2c-0, and — as seen today — can be broken by a second copy. Hardware sequencing belongs in the kernel (TECH_DEBT rows).
- **Design:** new ASoC component driver `sound/soc/codecs/fs1599.c` (local; copy in kernel-local/fs1599/, Kconfig/Makefile diff beside it). I2C 0x34 on the QUP SE1 bus (same as the KTD3136 backlight), regmap 8-bit register / 16-bit big-endian value. DAPM widgets IN → AMP → OUT; the AMP widget's POST_PMU runs reset/ready check + preset load + start_up, PRE_PMD runs shut_down (sequences ported 1:1 from tools/fs1599.py, which was verified on the phone). The preset (vendor `fs1599.fsm`, private) is parsed in the driver from built-in firmware (CONFIG_EXTRA_FIRMWARE together with the topology; build-m24.sh stages both under out/extra-fw), scene 6 from DT `foursemi,scene`. Wiring: DT node `amplifier@34` (`sound-name-prefix = "Spk Amp"`), sound card `aux-devs = <&spk_amp>` and route `"Spk Amp IN", "AUX"` (codec AUX output → amp input; DAPM turns the endpoint flags off for such chained pins, so the amp is powered only while the AUX path is active, i.e. Speaker device, not Earpiece). If the preset is missing the component still registers (earpiece/mic keep working) and logs "the amplifier will stay off".
- **Checked offline:** driver compiles clean for arm64 (sound/soc/codecs/fs1599.o); DT regenerated (gen-m17-dts.py). Not yet checked: full build, boot.
- **Userspace:** `audio/sky-amp-watch.service` now has `ConditionPathExists=!/sys/bus/i2c/drivers/fs1599` (inert on m24, still works on m22/m23 fallbacks) and `ConditionUser=!root`; deployed to the phone. The watcher, `sky-fs1599`, the udev rule and fs1599.py are removed from the rootfs build only after m24 is proven.
