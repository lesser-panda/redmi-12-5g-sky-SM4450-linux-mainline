# E030/E031：USB 主机、DisplayLink 扩展坞、FUSE/squashfs（m20）
日期：2026-11-12。用户陈述：把 USB-C 键盘和 USB 3.0 DisplayLink 坞接到手机，都没反应，要求构建。
## 本机证据（Debian m19，recovery_b 启动，2026-11-12）
- 端口角色 `/sys/class/usb_role/a600000.usb-role-switch/role` = host，但 `/sys/bus/usb/devices` 为空（连根集线器都没有）；内核配置 `# CONFIG_USB_XHCI_HCD is not set`、`# CONFIG_USB_STORAGE`、`# CONFIG_USB_RTL8152`、`# CONFIG_DRM_UDL`；`CONFIG_USB_DWC3_DUAL_ROLE=y`、`USB_ROLE_SWITCH=y`、`UCSI_PMIC_GLINK=y`。DT：dwc3 `dr_mode="otg"`、`usb-role-switch`、`maximum-speed="high-speed"`（没有 SS PHY，只有 USB2 速度），pmic-glink connector 已接。
- Debian 侧没有 `/lib/modules`、没有内核头文件、没有 DKMS；evdi 不能用 DKMS，要对 out/kbuild-m1 交叉构建（同 WiFi 模块做法）。
- FUSE/SQUASHFS/OVERLAY_FS/BINFMT_MISC 均未启用（Flatpak 的文档门户、AppImage 需要）。
## 路线
1. m20 = m19 + `USB_XHCI_HCD/PLATFORM`、`USB_STORAGE/UAS`、USB 以太网（RTL8152、AX88179、CDC）、`USB_ACM`、`SND_USB_AUDIO`、`FUSE_FS`、`SQUASHFS`(XZ/ZSTD/ZLIB)、`OVERLAY_FS`、`BINFMT_MISC`，全部内建。DT 不改。构建：用户运行 `! tools/build-m20.sh`（输出 out/candidates/m20）。
2. 先 RAM 启动验证（不写分区）：`fastboot boot out/candidates/m20/sky-m20-shim-boot-v4.img`，手机进 Debian 后插 USB-C 键盘，看 `/sys/bus/usb/devices`、`dmesg`。**不直接放进 recovery_b**——USB gadget 与 host 切换若有回归，会失去 PC 调试通道。
3. 判据 A（xhci）：插键盘后 sysfs 出现根集线器和键盘设备，按键有输入事件（evtest/libinput）。失败分支：看 dmesg 的 dwc3/xhci/ucsi 报错；若 VBUS 不供电（设备灯不亮），需要在 DT 里补 vbus 控制，先查 Android 的做法（pmic-glink / charger 固件 ADSP 负责 OTG）。
4. 判据 B（DisplayLink）：`tools/build-evdi.sh`（m20 之后运行）得到 out/evdi/evdi.ko；在 Debian 里 `insmod`；用户自行从 Synaptics 官网下载 aarch64 版 DisplayLinkManager（专有软件，EULA 由用户接受；不放仓库）安装；GNOME 应把 evdi 当作额外显示。USB2 速度下带宽有限，分辨率/刷新率要降。
5. 判据 C（FUSE 等）：`/dev/fuse`、`mount -t squashfs` 正常；`apt install flatpak fuse3` 后 flathub 的一个 arm64 应用能启动；AppImage 的 `--appimage-extract-and-run` 与普通方式都能跑。
## 回退
RAM 启动不写分区；失败就 `systemctl reboot` 或长按电源回 Android；recovery_b 里仍是 m19 的 v2 镜像（可用 `adb reboot recovery` / 音量上+电源 进入）。

## Speaker amplifier power saving (2026-11-12, E031 run 4; user asked to check "the amp power saving thing")
- **Problem (TECH_DEBT, AUDIO.md):** the UCM Speaker device switched the FS1599 on at selection and left it on all session (reg 0x11 = 0x00c0 even with the PipeWire sink suspended).
- **Cost measured (battery `current_now`, charger input suspended by the limiter, sink idle, m20 kernel, screen on):** amp on 192 / 201 mA, amp off 185 / 166 mA over four alternating 45 s windows → roughly 10–35 mA, about 21 mA (≈ 90 mW at 4.3 V) on average, i.e. ~10% of the idle draw. Noisy (WiFi etc.), order of magnitude only.
- **Fix (userspace, no kernel change):** `audio/sky-amp-watch` + `sky-amp-watch.service` (systemd user unit, enabled globally): follows the PipeWire node state of `alsa_output.*HiFi__Speaker__sink` from `pw-dump -m`; `idle`/`running` → amp on, `suspended`/gone → amp off; drives the FS1599 in-process via tools/fs1599.py (no interpreter start-up per switch). The UCM Speaker sequences no longer call sky-fs1599. Packaging: `audio/install-target.sh` + `tools/audio-stage.sh` (private/audio/stage.tar incl. the vendor preset); `tools/install-audio.sh` (live) and push-debian.sh/customize.sh (fresh rootfs) both use it; a fresh rootfs build previously had no audio setup at all.
- **Local machine verification (live phone, m20):** amp off (0x10=1, 0x11=0) while the sink is suspended after the watcher starts; a 1.5 s tone: amp on at stream start, off 5.2 s after the end (PipeWire's idle suspend), reg 0x11 0x0000 → 0x00c0 → 0x0000; two 0.6 s beeps 9 s apart: sink `running` at 21:13:28.881, `amp on` done at .978 (97 ms later, off takes ~25 ms), `suspended` 5 s after the end → amp off. Not reliable by instrument: the bottom-mic loopback at the quiet test volume read -69 dBFS baseline vs -74 dBFS during the tone (no usable signal), so whether sound is complete is a user-ear check.
- **Known cost of this design:** the amp comes on ~100 ms after the sink starts running, so the first ~0.1 s of a sound that starts from a cold amp can be clipped (short notification sounds most exposed). Long-term fix: the amplifier as a codec/DAPM component in the kernel, powered before the PCM trigger. Cheap knobs if it bothers: longer PipeWire `session.suspend-timeout-seconds` (keeps the amp warm between sounds, costs the saving), or accept.

- User confirmed (2026-11-12): the tone and both beeps were heard, so the amp watcher works end to end by ear (clipping of the first ~0.1 s not reported).

## E031 run 11: GNOME shows no charge-limit option although the kernel exposes the thresholds (2026-11-12 23:30, m22, local verification + UPower 1.90.9 source from sources.debian.org)
- **State:** `/sys/class/power_supply/battery/charge_control_{start,end}_threshold` = 75/80 (kernel limit works), but `org.freedesktop.UPower.Device` has `ChargeThresholdSupported=false` (Debian trixie: upower 1.90.9, gnome-control-center 48.4, gnome-shell 48.7).
- **Cause (source + measurement):** UPower does not look at the sysfs threshold files to decide support. `up_device_supply_battery_get_charge_control_limits()` (src/linux/up-device-supply-battery.c) only reads the udev property `CHARGE_LIMIT="start,end"`; without it `charge-threshold-supported` stays FALSE. The property comes from `60-upower-battery.rules` → hwdb lookup with the key `battery:<kernel>:<model_name>:<dmi modalias>`. The generic upstream entry is `battery:*:*:dmi:*` → `CHARGE_LIMIT=75,80`, so it only matches machines that have DMI. This phone is devicetree-only (no /sys/class/dmi): `systemd-hwdb query "battery:battery:<model>:"` returns nothing, the same key with `dmi:bvnX` appended returns `CHARGE_LIMIT=75,80`; `udevadm info` shows no CHARGE_LIMIT.
- **Consequence:** this is not a kernel problem and no kernel change can make UPower-based UIs show the option on a DMI-less machine (GNOME's panel is expected to read UPower, not verified in its source; KDE Plasma 6 also goes through UPower, not verified). ## E031 run 14: why does the suspend bounce? (2026-11-12 ~23:40–23:50, m22 from recovery_b, cable on the laptop, user asleep)
- **Tooling facts (local verification):** the m22 kernel has no CONFIG_PM_DEBUG (→ no /sys/power/pm_wakeup_irq, pm_debug_messages, pm_test; kernel/power/main.c lists them under CONFIG_PM_SLEEP_DEBUG), no ftrace, debugfs yes (wakeup_sources). DT has no cpu idle-states and no PSCI power domains although the firmware reports "OSI mode supported"; the RTC alarm cannot be used as a timer wake (SPMI write to 0x6146 is disallowed, the same register as the log spam), so an unattended suspend/wake test has no wake source other than power key / network.
- **Direct suspend (`echo mem > /sys/power/state`, WiFi up):** fails with `PM: Some devices failed to suspend, or early wake event detected` (suspend_stats: last_failed_errno −16, step `suspend`); the only wakeup sources that counted an event in that window are the WLAN driver's own (`mgmt_txrx tx_cmp`, `vdev_stop`), caused by the qcacld driver disconnecting during suspend ("hdd_cm_disconnect", local sky-c2c tracing). So with WiFi connected the vendor WLAN driver aborts the suspend by itself; logind/NetworkManager hides that by taking wlan0 down first.
- **Direct suspend with the WiFi radio off (`nmcli radio wifi off`, 4 s, then `echo mem`):** the phone then became unreachable on both WiFi (<phone-wifi-ip>) and USB (the gadget disappeared from the laptop) and stayed so for > 5 min; the monitor logged UNREACHABLE ×3 and exited (last good up=132 s). **Not yet known whether this is a real deep sleep (first one in this project) or a hang**; only the user's power-button press can tell (dmesg after wake will show the suspend duration; a hang would need a 10 s power hold, then Android boots, volume-up+power gives Debian from recovery_b). The IRQ/wakeup-source capture of that run (/root/irqw-*.txt on the phone) is lost until the phone is back.
- **If it was a real sleep:** the earlier 40 ms bounces were not "the firmware cannot sleep" but a wake event during the logind path (candidates: the USB/dock path, the WLAN sources, the BT UART wake line); then `echo mem` with WiFi off is the clean baseline and the dock case needs its own test.
- **Prepared, not built:** tools/build-m23.sh = m22 + CONFIG_PM_DEBUG + PM_ADVANCED_DEBUG so that /sys/power/pm_wakeup_irq names the wake IRQ of the next bounce. Needs `! tools/build-m23.sh` by the user (agent make is blocked).

## CORRECTION to runs 9, 10 and 14 (2026-11-13 ~00:00, local verification from the saved dmesg and the old Debian journal)
